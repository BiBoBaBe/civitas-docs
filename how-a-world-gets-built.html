The authoring pipeline

Playing happens through a screen. Authoring mostly happens through scripts. Everything below exists and is used, and several steps are run by hand. Each step says so rather than describing a button that does not exist.

1. A premise becomes a cast

Writing the people is the hand-written part. What you produce is a list: who they are, what they do, where they live, who they know, and what each of them wants and what it costs them, wired so the wants touch each other. One piece of automation is nearby: describe a world in a sentence and a model drafts the roster and the map, checked rather than trusted. It gives you the roster. It does not give you the people.

2. Each person becomes a character card

A card is the ordinary, portable kind. The card says who somebody is and how they talk; the world says where they are and what is happening; where they disagree, the world wins. Cards taken from an existing story carry a premise and a first message that assert things the world is about to contradict, so they are rebuilt as person-only copies: keep the looks, the voice, the history and the example dialogue, and strip the story they came from.

Cards carry an optional block the engine reads and other apps ignore: pronouns, secrets with trust gates, and an ordered list given up one item at a time. See People and feelings. Cards are matched to people by name, ignoring case and punctuation.

Today: generated by a script and posted to the character library by hand.

3. Each person gets a pinned look

A look is a base of what never changes and a small wardrobe by situation. Every look is checked before it can ship: the first tag has to state an adult, hair and eye colour belong to the base only, every garment needs a colour, and a list past a certain length is trimmed because the image model drops its tail.

Today: one table for the whole cast, edited by hand. Changing a look means rerunning the card script and reposting the card.

4. Each person gets one reference head

Render a portrait from the pinned look, crop the head and shoulders, save it. At render time it steers the face and hair. Somebody with no reference head still gets a picture, from their look tags alone.

Today: render, crop by hand, drop the file in, run the install script.

5. The people are seeded into a world

Then the world file: places that nest, who lives and works where, timetables, who knows whom, how they feel, what each of them is keeping, what is unfinished and what would count as it being over. A card for the simple case, code for the rest; see Writing a world card and Extending the engine. Either way it ends as a list of events in a log.

The world is then run forward from midnight before anybody plays in it, so the evening you walk into already has a day behind it.

6. Adding somebody to a world already being played

A session is its own log, so a person added to the seed after a session began is not in that world. The graft tool exists for that, and its restraint is the point:

  • Rooms inside places the save already has are added automatically, with their doors. Nothing that already exists is changed, because everything that exists has been lived in.
  • Adding a person is a dry run by default, and the whole plan is printed before anything is written.
  • The new person starts where their day has them at this hour, with their arrival backdated half an hour so nobody is announced walking into the room they work in.
  • Everything is written as authored with no significance, so none of it appears in anybody's journal.

A second mode brings people already in the save up to date with fields the seed has since grown. It fills only what is missing, lists any field with a different value and never applies it, and never touches a name, an identity or a card binding.

Today: a command with a save file, a dry run, and a warning to back the file up and not to run it while the world is live.

7. Repairing something recorded wrongly

Scene reading is not perfect. The answer is a small set of repair tags, adjudicated like anything else, so a bad repair is refused too. A correction is an event, not an edit. See What gets written down.

Today: repairs are issued as a request, not through a screen.

What is a button and what is not

StepToday
Playing: walking, waiting, paying, planning, texting, the phone and its appsButtons
Asking for a picture, the adult switches, the game master's viewButtons
Deleting a reply, which rewinds the worldA button
Drafting a world from a sentence, and loading a world cardA command
Writing the cast, the cards, the looksHand-written, then a script
Reference headsRender, crop, install by hand
Room artA chain of scripts against a graphics machine
Grafting somebody into a live saveA command, dry run first
RepairsA request, by hand
Making a world from inside the appNot built

All of it is repeatable. The parts that are scripts are scripts because they were built in the order the work needed them, not because they have to stay that way.
